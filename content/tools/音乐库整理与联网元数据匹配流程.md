# 音乐库整理与联网元数据匹配流程

本文记录一套适用于个人音乐库的整理方法：先保护原始数据，再建立可检索的目录结构，最后使用 MusicBrainz 等公开数据库补充专辑、曲目标签和封面。核心原则是：**可验证的自动化，不能确认的内容保持原样**。

## 一、总体思路

音乐库整理分成四层：

1. **连接层**：通过 SMB 访问音乐共享，不把密码写入脚本、日志或文档。
2. **文件层**：扫描、分类、隔离垃圾文件和重复文件，不直接删除原始内容。
3. **元数据层**：补充艺术家、曲名、专辑、曲号、年份和流派等标签。
4. **验证层**：重新读取文件，确认媒体仍可播放、标签写入成功、封面确实嵌入。

不要把四层混成一个不可逆的“自动整理”命令。每层都应该有独立的清单、日志和检查结果。

## 二、连接 SMB 共享

推荐使用独立的音乐库账户访问：

```text
//<服务器地址>/<音乐共享名>
```

浏览、索引和播放最好使用只读账户；只有用户明确授权文件整理时，才使用有写权限的账户。

连接成功后先确认：

- 共享名称正确；
- 当前账户确实进入了音乐目录；
- 能够列出目录和文件；
- 不会误操作 NAS 上的照片、备份、服务数据或个人资料目录。

密码只在临时命令或受保护的凭据文件中使用，不写入 Wiki、Git、终端日志或工作清单。

## 三、第一轮只读盘点

盘点阶段不修改文件，至少收集：

- 文件总数和总大小；
- 扩展名分布；
- 目录和每个目录的文件数量；
- 根目录散落的文件；
- 隐藏文件和 macOS AppleDouble 文件；
- 媒体文件是否能够被 `ffprobe` 读取；
- 音频是否已有 Artist、Title、Album、Track、Date、Genre 标签。

不要只用文件扩展名判断文件类型。导入过程中可能出现扩展名为 `.mp3` 或 `.flac`、但实际只有几 KB 的伪文件；这类文件必须用媒体工具验证。

## 四、目录设计

推荐使用“分类目录 + 艺术家目录 + 收件箱”的结构：

```text
Music/
├── Artists/
├── Japanese Learning/
├── Japanese Music/
├── Anime/
├── Soundtracks/
├── Podcasts/
├── Videos/Music Videos/
├── Inbox/
└── _Archive/
    ├── Duplicates/
    ├── macOS-Metadata/
    ├── Suspicious-4KB/
    └── metadata-backups/
```

### 分类规则

- 明确的艺术家目录放入 `Artists/<艺术家>/`；
- 日语听力和教材放入 `Japanese Learning/`；
- 日语音乐合集放入 `Japanese Music/`；
- 动漫歌曲放入 `Anime/`；
- 影视或动画原声放入 `Soundtracks/`；
- Podcast 与音乐分开；
- WebM、MP4 等视频放入 `Videos/Music Videos/`；
- 无法可靠判断归属的文件先放入 `Inbox/`；
- 新下载文件先进入 `Inbox/`，处理完成后再归档。

## 五、垃圾文件和异常文件

### macOS 文件

以下文件通常不是音乐内容：

```text
.DS_Store
._*
```

不要直接删除，先移动到：

```text
_Archive/macOS-Metadata/
```

移动时保留相对路径，方便追溯来源。

### 4096 字节伪音频

如果一个 `.mp3` 或 `.flac` 文件：

- 大小只有 4096 字节左右；
- `ffprobe` 无法读取；
- 没有有效音频流；

则将其视为导入残留或 AppleDouble 异常文件，移动到：

```text
_Archive/Suspicious-4KB/
```

保留说明文件，绝不把它们当作正常音频写入标签。

## 六、重复文件处理

重复检测分两级：

1. 先按文件大小筛选候选；
2. 再对正常大小的媒体计算 SHA-256。

只有哈希完全一致时，才称为“精确重复”。

处理方式：

- 保留一个规范副本；
- 其他副本移动到 `_Archive/Duplicates/`；
- 记录原路径、目标路径、文件大小和哈希；
- 不因为文件名相似就删除或合并。

例如简体和繁体文件名可能是不同版本，不能仅凭曲名判断重复。

## 七、元数据补全逻辑

标签补全遵循“强证据优先”：

### 可以自动补充

- 已存在的嵌入标签：保留，不覆盖；
- `Artists/<艺术家>/`：可推断艺术家；
- `艺术家 - 歌曲名.ext`：可解析艺术家和曲名；
- `01_歌曲名.ext`：可解析曲号和曲名；
- 明确的合集目录：可推断合集名和内容类别。

### 不应猜测

- 发行年份不能用文件修改时间代替；
- 单曲不能仅凭艺术家名推测专辑；
- 流派不能为了完整率随便填写；
- 不明确的封面不能自动下载；
- 同名歌曲不能只按标题匹配，必须结合艺术家、曲目数量或曲目顺序。

第一轮只填写空字段，不覆盖已有非空标签。推荐优先处理：

```text
Artist
Title
Track number
```

## 八、联网匹配专辑和封面

### 工具优先级

优先使用成熟工具和公开数据库：

- `ffprobe`：验证媒体和读取基础信息；
- Python `mutagen`：读写 MP3 ID3、FLAC Vorbis Comments 和嵌入图片；
- Beets：作为 MusicBrainz 自动匹配工具，但必须使用隔离配置和 dry-run；
- MusicBrainz：专辑、发行版本、曲目、艺术家和年份来源；
- Cover Art Archive：同一发行版本的封面来源。

如果 Beets 没有给出清晰匹配，不要继续强行导入。可以直接查询 MusicBrainz API，但仍然要人工定义匹配条件。

### 高置信度匹配条件

一个合集只有在以下条件同时满足时才适合自动写入：

- MusicBrainz 返回的专辑名明确；
- 艺术家或 Various Artists 身份合理；
- 本地曲目数量与在线曲目数量一致；
- 曲号顺序一致；
- 多数曲名精确对应；
- 发行版本没有明显的语言、地区或曲目差异；
- Cover Art Archive 有对应封面。

匹配成功后：

1. 保存写入前的全部标签；
2. 写入艺术家、曲名、专辑、曲号和年份；
3. 只在来源明确时写入流派；
4. 下载同一发行版本的正面封面；
5. 同时嵌入 MP3 和 FLAC；
6. 在专辑目录中保留一份 `cover.jpg`；
7. 写入 MusicBrainz Release ID 和处理报告。

## 九、MP3 与 FLAC 的写入差异

MP3 使用 ID3 Frame，不能把普通字符串直接写入 Frame：

```text
TIT2  曲名
TPE1  艺术家
TALB  专辑
TRCK  曲号
TDRC  年份
TCON  流派
APIC  嵌入封面
```

FLAC 使用 Vorbis Comments 和 Picture Block：

```text
TITLE
ARTIST
ALBUM
TRACKNUMBER
DATE
GENRE
Picture
```

使用 `mutagen` 写入 MP3 时，必须使用 `TIT2`、`TPE1`、`TALB`、`TRCK`、`TDRC`、`TCON` 等 Frame 类；FLAC 标签使用列表值，并使用 FLAC Picture Block 写入封面。

## 十、验证流程

任何批量写入完成后必须再次验证：

- 文件数量没有意外减少；
- `ffprobe` 可以读取所有正常媒体；
- 艺术家、曲名、专辑、曲号和年份存在；
- MP3 存在 `APIC`；
- FLAC 存在 Picture Block；
- 封面文件是有效 JPEG/PNG；
- 精确重复文件没有再次出现在正式目录；
- 整理日志和标签备份可读取。

建议分别统计 MP3 和 FLAC 的封面数量，不能只用简化标签读取器判断 MP3 是否有封面，因为 EasyID3 视图通常不会显示 APIC。

## 十一、备份、日志与回滚

每次批量操作至少保留：

```text
整理记录.json
metadata-before.json
metadata-before-musicbrainz-<collection>.json
musicbrainz-<artist>-report.json
```

记录内容包括：

- 操作时间；
- 原路径和目标路径；
- 文件大小；
- 哈希；
- 使用的数据库和 Release ID；
- 修改了哪些字段；
- 封面来源；
- 错误和未匹配文件。

回滚时先检查目标是否已经存在更新版本，禁止直接覆盖。文件移动回滚和元数据回滚必须分开处理。

## 十二、实际工作中的决策原则

### 可以自动化的事情

- 统计和扫描；
- 识别扩展名与媒体有效性；
- 隔离明显的系统垃圾文件；
- 隔离 4096 字节伪音频；
- SHA-256 精确重复检测；
- 根据明确目录和文件名补 Artist、Title、Track；
- 对曲目数量、顺序和艺术家都匹配的合集联网补标签和封面。

### 必须保守处理的事情

- 在线数据库的同名专辑；
- 中文或日文单曲的专辑归属；
- YouTube 下载文件的发行年份；
- 简繁体或不同版本是否相同；
- 仅有相似标题但没有艺术家信息的文件；
- 流派和封面来源不明确的内容。

最终目标不是让每个字段都有值，而是建立一个可靠、可检索、可回滚的音乐库。空标签比错误标签更容易修复。
