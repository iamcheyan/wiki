# Hermes state.db 备份与恢复设计要点

本文整理适用于 Hermes SQLite 状态库的通用备份原则。具体表结构、索引、命令和迁移方式会随 Hermes 版本变化；执行前应检查当前版本的源码和官方文档，不要把某台机器的数据库布局当成永久规范。

## 一致性快照

- 不要在 Hermes 正在运行时直接复制 SQLite 数据库主文件并假设副本完整；数据库可能使用 WAL，近期事务可能仍在 WAL 文件中。
- 优先使用 SQLite Online Backup API 或 `VACUUM INTO` 制作一致性快照；必要时通过只读连接读取源库。
- 压缩、拆分或重建索引都只针对快照副本操作，避免直接改写运行中的数据库。
- 备份前后记录文件大小、校验和与版本信息；不要把日志、配置中的凭据或个人数据放入公开资料。

## 全文搜索索引

全文搜索索引可能占用明显空间，但它可能依赖特定虚拟表、触发器、辅助表和 schema 版本。只有在确认当前 Hermes 版本的表结构、触发器和恢复要求后，才能考虑单独处理索引。

如果备份方案选择不携带可重建的索引，必须同时保存与该快照对应的 schema/DDL，并在恢复副本上按受支持的方式重建。不能只删除看起来体积大的表，也不能假设触发器或增量状态在删表重建后仍然正确。

## 大文件限制与分片

若存储服务对单文件大小有限制，可在压缩后仍超限时对归档文件分片。分片必须有明确顺序和完整性校验；恢复前先合并并验证归档结构，不能把分片当作独立备份。

## 恢复验收

“备份命令成功”不等于能够恢复。定期在隔离副本上完成一次完整演练：

1. 从备份还原到临时目录，不覆盖正在运行的数据库；
2. 检查 SQLite 完整性、schema 版本和关键表记录数；
3. 验证全文检索和其他依赖索引的功能；
4. 确认 Hermes 能以该版本读取恢复副本；
5. 记录还原步骤、验证结果和未解决限制。

数据保留策略、剪枝和数据库迁移会影响历史会话，不应仅为了缩小备份而开启或执行；先确认产品行为和恢复需求，再决定是否采用。
